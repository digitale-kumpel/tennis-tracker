## Vorgehen

- `next` (und `eslint-config-next`) auf die neueste Version derselben Hauptlinie, die alle Funde behebt: 16.2.x bzw. 14.2.x. Kein Major.
- Basis-Image: Node 20 ist seit 30.04.2026 EOL, deshalb auf `node:22-alpine` (chriscut hat es schon). `tar` kommt über das npm im Basis-Image. Steht danach noch ein CRITICAL in npm-Paketen des Laufzeit-Images, wird npm in der Runner-Stage entfernt, weil `next start`/`server.js` es nicht braucht.
- Lockfile im selben Commit neu (`npm install` mit dem neuen Pin, danach `npm ci` muss durchgehen).
- Deploy: Die Planvorlage ging von einem Workflow `deploy-nextjs-production.yml` aus. Den gibt es in diesem Repo nicht, maßgeblich ist der Rollout-Weg unter „Ergebnis“ (Handbuild, Tag-Bump im Manifest; Build-Workflow fehlt, Fundstück KUC-254). Rollout nur Mo–Do 08:00–16:00.

## Szenarien

- KUC-231 S1: Gegeben das neue Lockfile, wenn der Build-Weg des Dockerfiles `npm ci && npx prisma generate && npm run build` im Repo-Wurzelverzeichnis läuft, dann endet er mit Exit 0. (Angepasst gegenüber der Vorlage: `prisma generate` ist hier Teil der Build-Stage, ohne den generierten Client scheitert der Typecheck unabhängig von dieser Änderung.)
- KUC-231 S2: Gegeben das neu gebaute Image, wenn `trivy image --severity CRITICAL` es scannt, dann zeigt es 0 CRITICAL.
- KUC-231 S3: Gegeben das neu gebaute Image, wenn es lokal startet und `/` abgerufen wird, dann antwortet es mit HTTP 200.
- KUC-231 S4 (nach dem Rollout): Gegeben der neue Tag im Cluster, wenn der Trivy-Operator neu gescannt hat, dann sind die Funde geschlossen.
